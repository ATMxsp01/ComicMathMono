# 组合重音符号（combining marks）：要不要收录、以什么宽度收录

> 这是 [`locl-issue.md`](locl-issue.md) 的姊妹篇。`locl` 那篇讲"合并字体把数字弄没了"，
> 这篇讲"带重音的字母 / 组合符号该怎么处理"。
> 结论一句话：**收录为 0 宽，让排版引擎自己定位。**

## 1. 背景：带重音字母有两种写法

| 写法 | 例子 | 码点 |
|---|---|---|
| **预组合**（NFC） | `é` | U+00E9（一个码点） |
| **分解** | `e` + `◌́` | U+0065 + U+0301 |

`U+0301 COMBINING ACUTE ACCENT` 的类别是 `Mn`（Mark, nonspacing，非间距标记），
按 Unicode 语义是"**叠加到前一个字符上、自己不占位置**"。
分解形式常见于：从 PDF/网页复制、某些输入法、越南语等、以及程序做 NFD 规范化时。

## 2. 三个角色：谁决定什么

| 角色 | 决定的事 |
|---|---|
| **Unicode** | 语义：U+0301 是"非间距标记，叠加到前一字符" |
| **字体** | 外形：该码点的字形轮廓 + 字形坐标（相对笔位）+ advance |
| **排版引擎**（HarfBuzz / 浏览器 / 终端） | 最终落点：把标记放到哪一格 |

不同字体给同一个 `U+0301` 的坐标差别可以很大（实测）：

| 字体 | advance | 轮廓 x 范围 | 说明 |
|---|---|---|---|
| JuliaMono | 1200（=1 格） | [398, 800] | 居中在自己格子里 |
| Noto Sans Mono | 0 | [−41, 160] | 左锚定，配 GPOS 用 |
| ComicShanns / 本字体（旧） | 无此字形 | — | — |

## 3. 关键机制：HarfBuzz 会先"合成"

HarfBuzz（浏览器、编辑器、kitty 都用它）在整形前会做归一化：
**如果 `基字母 + 标记` 能合成一个预组合码点、且字体有这个字形，就直接合成。**

实测本字体（收录标记之前）：

```
e + U+0301        -> 单个字形（= é）          ✅ 合成
o + U+0302+U+0301 -> 单个字形（= ồ）          ✅ 合成
c + U+0301        -> 单个字形（= ć）          ✅ 合成
q + U+0301        -> q + .notdef(豆腐块)      ❌ 无预组合形式 → 缺字形
x + U+0327        -> x + .notdef              ❌ 同上
```

也就是说：**有预组合形式的序列在任何场景都正常**（本字体已含全部拉丁预组合字母）；
只有**没有预组合形式**的序列（`q+́`、`x+̧` 这类）才需要用独立的标记字形。

## 4. 没有 GPOS 也能定位

收录标记后，本字体仍然**没有 GPOS**（不复制上游 GPOS）。
但实测 HarfBuzz 会做**回退定位**，把标记挪回基字符所在格子：

```
q + U+0301  ->  (q, x_advance=550, x_offset=0) + (标记, x_advance=0, x_offset=-368)
```

`x_offset=-368` 表示标记被整体左移，落在 `q` 的格子里。
所以无论是终端（kitty）还是浏览器，都能正确叠加——**不需额外给 `q́` 造预组合字形**。

## 5. 本项目的决定

- **收录 JuliaMono 的组合标记**（U+0300–036F、U+1AB0–1AFF、U+1DC0–1DFF、
  U+20D0–20FF、U+FE20–FE2F，见 `build.py` 的 `JULIA_COMBINING_RANGES`）；
- 复制后用 `zero_width_marks()` 把 **Mn/Me 字符的 advance 全部置 0**；
- 拷贝时跳过 Noto 已有的码点（如 `U+20E3` 键盘帽组合符属于 emoji 序列，保留 Noto 版）。

好处：消除"豆腐块"，字体自包含，不依赖系统里一定有合适的回退字体。

## 6. 已知取舍

- **定位精度**：没有 GPOS，落点靠 HarfBuzz 回退定位，可能比"原生 GPOS 锚定"略偏；
  若将来要更精确，可以给字体自动生成 GPOS `mark` 锚定。
- **`U+20E3` 键盘帽**：`1️⃣`（`0031 FE0F 20E3`）目前不会合成成单个 emoji 字形，
  而是渲染成"数字 + 键盘帽框"两个字形。这是**合并引入字形重命名**导致的既有问题，
  与本文的组合符决策无关，可另行修。
- **终端差异**：不同终端对组合符的处理不完全一致；本字体给出 0 宽 + 合理坐标，
  属于"最不容易出错"的形态。
