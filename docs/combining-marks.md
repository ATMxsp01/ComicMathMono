# 组合重音符号（combining marks）：要不要收录、以什么宽度收录

> 这是 [`locl-issue.md`](locl-issue.md) 的姊妹篇。`locl` 那篇讲"合并字体把数字弄没了"，
> 这篇讲"带重音的字母 / 组合符号该怎么处理"。
> 结论一句话：**收录为 0 宽，让排版引擎自己定位。**

## 1. 背景：带重音字母有两种写法

| 写法 | 例子 | 码点 |
|---|---|---|
| **预组合**（NFC） | `é` | U+00E9（一个码点） |
| **分解** | `e` + `◌́` | U+0065 + U+0301 |

`U+0301 COMBINING ACUTE ACCENT` 的类别是 `Mn`（Mark, nonspacing，非间距标记），
按 Unicode 语义是"**叠加到前一个字符上、自己不占位置**"。
分解形式常见于：从 PDF/网页复制、某些输入法、越南语等、以及程序做 NFD 规范化时。

## 2. 三个角色：谁决定什么

| 角色 | 决定的事 |
|---|---|
| **Unicode** | 语义：U+0301 是"非间距标记，叠加到前一字符" |
| **字体** | 外形：该码点的字形轮廓 + 字形坐标（相对笔位）+ advance |
| **排版引擎**（HarfBuzz / 浏览器 / 终端） | 最终落点：把标记放到哪一格 |

不同字体给同一个 `U+0301` 的坐标差别可以很大（实测）：

| 字体 | advance | 轮廓 x 范围 | 说明 |
|---|---|---|---|
| JuliaMono | 1200（=1 格） | [398, 800] | 居中在自己格子里 |
| Noto Sans Mono | 0 | [−41, 160] | 左锚定，配 GPOS 用 |
| ComicShanns / 本字体（旧） | 无此字形 | — | — |

## 3. 关键机制：HarfBuzz 会先"合成"

HarfBuzz（浏览器、编辑器、kitty 都用它）在整形前会做归一化：
**如果 `基字母 + 标记` 能合成一个预组合码点、且字体有这个字形，就直接合成。**

实测本字体（收录标记之前）：

```
e + U+0301        -> 单个字形（= é）          ✅ 合成
o + U+0302+U+0301 -> 单个字形（= ồ）          ✅ 合成
c + U+0301        -> 单个字形（= ć）          ✅ 合成
q + U+0301        -> q + .notdef(豆腐块)      ❌ 无预组合形式 → 缺字形
x + U+0327        -> x + .notdef              ❌ 同上
```

也就是说：**有预组合形式的序列在任何场景都正常**（本字体已含全部拉丁预组合字母）；
只有**没有预组合形式**的序列（`q+́`、`x+̧` 这类）才需要用独立的标记字形。

## 4. 现在有了 GPOS `mark` 定位（2026-10 追加）

最初这个字体**没有 GPOS**，靠 HarfBuzz 的回退定位。实测发现**对本字体是错的**：

```
q + U+0301：基准 'q' 墨迹 x=[66,499]（格子中心 275）
            组合符 'acutecomb' 墨迹 x=[364,549] —— 中心 456，偏右 +182，贴到格子右半边
```

原因是 JuliaMono 的组合符是按「**550 宽格子居中 + 基线对齐**」设计的
（acutecomb 自身墨迹 x=[182,367]，中心正好 275），而 HarfBuzz 在没有 GPOS 时用的启发式
假设标记是「设计在基字之后的笔位」，于是把它推到了右边。

所以 `build.py` 现在会生成一个 GPOS `mark` 特性（400 个组合符），锚点取 `(格子中心, 基线)`：

```python
markClass [<400 个组合符>] <anchor 275 0> @MC;
feature mark { position base [<所有非标记字形>] <anchor 275 0> mark @MC; } mark;
```

> **不能只用 `unicodedata.category()` 判 Mn/Me**：Python 3.13 的 Unicode 数据是 15.1，
> 而 JuliaMono 快照已到 Unicode 16 —— `U+1ACF..U+1ADD`、`U+1AE0..U+1AE5` 这 21 个新组合符
> 会被判成 `Cn`（未分配），从而**既没 0 宽化、也没进 GPOS mark**（fontbakery 的
> `gdef_mark_chars` 会报）。`build.py` 用 `is_combining_mark()`（区块判定 ∪ 类别）来兜底。

标定过程中确认了一个容易搞错的细节：**HarfBuzz 在应用 mark-to-base 时还会再减去基准字形的
advance**，所以「锚点 x 相同」才会得到「刚好左移一格」的位移（-550）：

| base 锚点 | mark 锚点 | 实测 x_offset |
|---|---|---|
| (0, 0) | (550, 0) | −1100 |
| (275, 0) | (275, 0) | **−550** ✅ |

结果：`q + U+0301` 的墨迹变成 `[182,367]`，中心 274 ≈ 格子中心 275 —— 完全对齐。

> 实现细节：fea 语法里 `A-B` 会被当成**字形范围**，所以名字含 `-` 的字形
> （例如 Nerd Font 的 `ON-OFF`）不能写进 fea，构建时直接跳过（它们是图标，不需要当基准）。

## 4b. 没有 GPOS 时的回退行为（历史）

收录标记后，本字体仍然**没有 GPOS**（不复制上游 GPOS）。
但实测 HarfBuzz 会做**回退定位**，把标记挪回基字符所在格子：

```
q + U+0301  ->  (q, x_advance=550, x_offset=0) + (标记, x_advance=0, x_offset=-368)
```

`x_offset=-368` 表示标记被整体左移，落在 `q` 的格子里。
所以无论是终端（kitty）还是浏览器，都能正确叠加——**不需额外给 `q́` 造预组合字形**。

## 5. 本项目的决定

- **收录 JuliaMono 的组合标记**（U+0300–036F、U+1AB0–1AFF、U+1DC0–1DFF、
  U+20D0–20FF、U+FE20–FE2F，见 `build.py` 的 `JULIA_COMBINING_RANGES`）；
- 复制后用 `zero_width_marks()` 把 **Mn/Me 字符的 advance 全部置 0**；
- 拷贝时跳过 Noto 已有的码点（如 `U+20E3` 键盘帽组合符属于 emoji 序列，保留 Noto 版）。

好处：消除"豆腐块"，字体自包含，不依赖系统里一定有合适的回退字体。

## 6. 已知取舍

- **定位精度**：已生成 GPOS `mark` 锚定（见第 4 节），横向回到格子中心；
  第一个标记的纵向保持设计位置（基线对齐）；mark-to-mark 的第二个标记按两端墨迹
  （`yMax(first) − yMin(second)`）逐字形定位。
- **叠加规则是"贴顶/贴底"**：已生成 mark-to-mark。每个标记按自身墨迹分成 above / below
  两类，第二个同类标记会落在前一个的墨迹顶（above）或底（below）上；跨类（above 后跟 below）
  仍回落到 mark-to-base 的设计位置。锚点用逐字形精确值（不再量化 20 单位）。
- **预组合字母 + 额外标记**：HarfBuzz 会先把 `a + U+0301` 合成 `aacute`。如果后面还有
  第二个组合符，单靠 mark-to-mark 看不到「第一个标记」，第二个标记会落回基线。构建时加
  一条 contextual `ccmp` 规则：**预组合字母后面跟着组合符时**才拆回基字母 + 组合符，
  于是 `á + U+0304`、`a + U+0301 + U+0304`、`α + U+0301 + U+0304` 都能正确叠高。
- **终端 cell 收格**：四个 face 的所有 Letter 都做水平压缩/居中并留 25 单位侧边距；
  斜体/粗斜体还额外收数字、标点、货币与数学符号。希腊多调号预组合字母
  （U+1F5B 墨迹 877 单位宽）也在其中。SeriousShanns 斜体最多越界约 70 单位
  （`C/E/I`、`d`、`/`、`%`），而 kitty 会按 cell 边界裁切，所以必须收格。
- **脚本注册**：`mark` 特性注册在 `DFLT` + `latn/grek/cyrl/hebr/arab/armn/geor` 下。
  实测只注册 `DFLT` 时，希伯来文会退回 HarfBuzz 的启发式定位（偏移全是猜的）。
- **`U+20E3` 键盘帽**：`1️⃣`（`0031 FE0F 20E3`）曾因"合并重命名"失效（渲染成"数字 + 帽框"
  两个字形）。已由 `build.py` 的 `revive_renamed_rules()` 修复，详见
  [`merge-renaming.md`](merge-renaming.md)。
- **终端差异**：不同终端对组合符的处理不完全一致；本字体给出 0 宽 + 合理坐标，
  属于"最不容易出错"的形态。
