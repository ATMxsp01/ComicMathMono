# 安装时的一个陷阱：`fc-cache -f` 会把正在运行的终端搞崩

这篇不是字体本身的问题，而是**安装字体时的操作**踩到的坑 —— 但它非常隐蔽：
崩溃看起来像"字体有问题"，实际上和字体内容无关。

## 现象

在终端（kitty）里执行：

```bash
cp dist/ComicMathMono-*.ttf ~/.local/share/fonts/ComicMathMono/
fc-cache -f
```

终端**当场或随后不久直接消失**（不是报错退出，是进程被杀）。之后即使不再跑 `fc-cache`，
**过一段时间又会崩一次**，看起来毫无规律。

## 原因

fontconfig 的缓存（`~/.cache/fontconfig/*.cache-*`）是**通过 `mmap` 映射进进程**的。
`fc-cache -f` 重建缓存时会**截断并重写**这些文件。于是：

1. 正在使用该映射的进程（kitty 通过 fontconfig 查字体）读到的是**已被截断/替换的页面**；
2. 对失效映射的访问会触发 **`SIGBUS`**，进程被内核直接杀掉 —— 没有异常栈、没有日志，看起来就是"窗口没了"；
3. 即使这一次没崩，**被破坏的映射会留在进程里**，之后任何一次新的字体查找
   （例如渲染一个之前没渲染过的字符）都可能再次触发 `SIGBUS` —— 这就解释了"为什么后来又崩了"。

## 正确做法

**不要预热缓存。** fontconfig 会按目录 mtime 自动失效缓存，`cp` 完新字体后直接就能被找到。

如果需要重建缓存（例如缓存真的坏了），请在**另一个终端**里做，或者先关掉所有使用该缓存的程序：

```bash
rm -rf ~/.cache/fontconfig
fc-cache -f
```

## 附带的一条：不要原地覆盖字体文件

`cp` 覆盖正在使用的字体文件同样有风险 —— 写入过程中的**半成品文件**可能被正在查字体的程序读到。
本项目 [`install.sh`](../install.sh) 的做法是**先写临时文件、再 `mv` 覆盖**（`rename` 是原子操作）：

```bash
tmp="$DEST/.${base}.tmp"
cp "$f" "$tmp"
mv -f "$tmp" "$DEST/$base"
```

这样任何时刻目录里看到的都是一个完整文件。

## 小结

| 做法 | 结果 |
|---|---|
| `cp` 覆盖 + `fc-cache -f`（终端运行中） | ❌ 进程 `SIGBUS`，且会持续复发 |
| `cp`（原地覆盖，无 fc-cache） | ⚠️ 通常没事，但理论上可能读到半成品 |
| `cp` + `mv`（原子替换，无 fc-cache） | ✅ 推荐 —— `install.sh` 采用 |
