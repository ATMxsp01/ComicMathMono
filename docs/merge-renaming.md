# 合并字体的第三个坑：Merger 的字形重命名会让排版规则失效

> `locl-issue.md`（数字消失）、`combining-marks.md`（组合符）之后的第三篇。
> 这篇讲 **fontTools `Merger` 重命名字形** 带来的副作用，以及 `keycap emoji`（`1️⃣`）
> 为什么坏掉、怎么修。修复函数是 `build.py` 里的 `revive_renamed_rules()`。

## 1. 现象

`1️⃣`（`U+0031 U+FE0F U+20E3`）本该合成成**一个彩色键盘帽字形**，
但在合并字体里渲染成了 **「数字 1」+「键盘帽框」两个字形**，看起来像 `1⃞`。
`0️⃣`–`9️⃣`、`#️⃣`、`*️⃣` 共 12 个全部如此。

## 2. 机制

`fontTools` 的 `Merger` 在合并时，遇到**两个字体有同名、但轮廓不同的字形**，
会把**后一个字体**的字形改名（文档明确写：`parenleft` → `parenleft.1`）。
这在 cmap 层面是合理的（避免互相覆盖），但会连累引用这些字形的排版规则：

```
base(Comic)  : cmap[U+0031] = 'one'        ← 轮廓 A
Noto         : cmap[U+0031] = 'one'        ← 轮廓 B（不同）

Merger 合并后：
  · 把 Noto 的 'one' 改名成 'one.1'
  · Noto 的 ccmp 连字规则   ['one','uni20E3'] → 键盘帽
    被同步改写成            ['one.1','uni20E3'] → 键盘帽
  · cmap[U+0031] 仍然 = 'one'（base 的那个）

结果：排版时 U+0031 产出的字形是 'one'，
     而规则的第一项是 'one.1' → 永远匹配不上 → 规则失效
```

实测（合并后、保存前的**内存**字体）：

```
带 .N 后缀的字形 44 个：
  space.1 numbersign.1 asterisk.1 zero.1 one.1 ... nine.1 trademark.1 uni2139.1 ...
ccmp 连字: ['one.1','uni20E3'] -> 'uFE82E'
cmap[U+0031] = 'one'
```

再保存成 `post` format 3.0 后，字形名丢失，`one.1` 变成 `glyph18442`，
从字形名上再也看不出它是谁 —— 排查时极具迷惑性：

```
keycap 连字 12 条全部"死规则"：
  ['glyph18442','uni20E3'] -> uFE82E     (glyph18442 不在 cmap 里)
  ... 共 12 条，0 条有效
```

## 3. 修复

`revive_renamed_rules(font, noto)`：合并完成后、保存前执行——

1. 从 Noto 源字体的 cmap 建立 `字形名 → 码点` 反查表；
2. 扫描合并后字体里所有 `X.N` 形式的字形名，用 `X` 反查出码点，再取
   **合并后 cmap 里该码点对应的字形**作为目标；
3. 把 GSUB/GPOS 里对这些"被改名副本"的引用统统改回目标字形。

```
'one.1'      → cmap[U+0031] = 'one'        （base 的数字，可达）
'uni2139.1'  → cmap[U+2139] = 'uni2139'
```

被改名副本本身就**不可达**（没有任何 cmap 指向它），引用它的规则必然失效，
所以"改回同码点字形"是唯一合理的修复。

修复效果（HarfBuzz 实测）：

```
1️⃣  -> 1 个字形 (advance 1100)   ✅ 彩色键盘帽
9️⃣  -> 1 个字形                  ✅
#️⃣  -> 1 个字形                  ✅
🇨🇳 -> 1 个字形                  ✅ 国旗（本来就没坏）
```

## 4. 同一根源的另一个现象（尚未处理）

同一套"重命名 / base 优先"的规则，还让 **45 个码点显示的是 base 的字形，
而不是 Noto 的彩色 emoji**：

```
space  #  *  0-9                      （ASCII，本来就应该用 base）
™  ℹ                                  （U+2122 U+2139，来自 Julia 的字母式符号区）
↔ ↕ ↖ ↗ ↘ ↙ ↩ ↪                        （U+219x，来自 Julia 的箭头区）
⌚ ⌛ ⌨ ⏏ ⏩ ⏪ ⏫ ⏬ ⏭ ⏮ ⏯ ⏰ …            （U+23xx，来自 Julia 的技术符号区）
```

其中 `↔ ↩ ™ ℹ` 这类默认是**文本呈现**，用 base 的单色字形是合理的；
但 `⌚ ⏰ ⏩ ⏬` 这类在 Unicode 里是 **Emoji_Presentation=Yes**（默认就该是彩色 emoji），
现在却显示成单色符号 —— 属于"要不要让 emoji 赢"的策略问题，需要单独决定。

（`U+25CC` 点圈和 Default_Ignorable 字符在 `Merger` 里本来就被跳过，不受影响。）
